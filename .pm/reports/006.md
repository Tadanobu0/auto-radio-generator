## 調べたこと

### 1. 画像の生成(プロンプト・ComfyUI・時間・キャッシュ)
- **流れ**: `TimelineCalculator.calculate_timeline` がセグメント(= 章)ごとに `ImageProvider.get_image_for_segment` を 1 回呼ぶ → `ImagePromptGenerator.generate_prompt`(LLM。DSV4 を Mac Studio Proxy 経由で呼ぶ。curator_model、temperature 0.8)が英語プロンプトを作る → `ComfyUIClient.generate_image`
- **LLM に渡しているもの**: 章タイトル + 本文の抜粋。抜粋は「先頭 10 ターン(16 ターン以上の章は先頭 12 + 中ほど 2 + 最後の 2)をつなげて **800 字で切る**」。4〜5 分の章(30〜50 ターン)だと、**先頭 1 分ほどしか見ていない**。要約はしておらず、LLM が抜粋から「核になる場面を 1 つ」選んでいる
- 指示文(`SYSTEM_PROMPT_TEMPLATE`)と、章の種類ごとの構図の指示(`_get_composition_guidance`)は `services/script_generation/image_prompt_generator.py` にある。出力の先頭に、コードで「人・手・顔・文字・画面の無い場面」の固定の前置きを付けている。1000 字を超えたら固定の代わりのプロンプト(`_get_fallback_prompt`)に差し替える
- **色・雰囲気**: `VisualPaletteGenerator` が番組タイトルと概要から決めた色・美学(visual_identity)を全章に共通で入れる
- **ComfyUI**: `config/workflow_api.json`。FLUX.1 [schnell] fp8(`flux1-schnell-fp8.safetensors`)、**768×432、4 ステップ、cfg 1.0**、euler / normal、seed は毎回ランダム。動画では 1920×1080 に 2.5 倍に拡大して使っている
- **1 枚あたりの時間**: リポジトリにも手元にも実測値が無い。実測は Windows のセッションの `videos/generation_metadata.jsonl`(`generation_time_sec`)と `prompt_report.md` に毎回残っている。設定からの見積もりは、RTX 4070 + schnell 4 ステップ + 768×432 で **1 枚 4〜8 秒**(ComfyUI のポーリングが 2 秒刻みなので、その分を含む)。最初の 1 枚はモデルの読み込みで 20〜60 秒。これとは別に、LLM のプロンプト生成が 1 枚ごとに数秒〜10 秒ほどかかる。生成は 1 枚ずつ順番(semaphore 1、章のループも直列)
- **キャッシュ**(`output/.image_cache/`): キーは **プロンプト全文の SHA-256**。プロンプトは temperature 0.8 の LLM が毎回作るので、同じ台本で作り直しても、**ほぼ当たらない**。当たるのは代わりのプロンプトに落ちたときだけで、その場合は章の種類と色が同じなら**別の回でも同じ絵が使い回される**。消す仕組みは無い(溜まる一方)。パスは作業ディレクトリからの相対

### 2. 枚数を増やす余地
- **区切りに使える情報**:
  - 発話ごとの時刻は音声合成の中にもうある(`calculate_segment_timings` の `phrase_data`。1 ターン = 1 フレーズ)。今は章の頭と終わりしか外に出していないので、**章の中の各ターンの開始時刻を `SegmentTiming` に足せば、ターンの境目で絵を切り替えられる**
  - 台本の構造: `show_spec.topics[i].key_claims` に、章ごとの論点 3〜4 個と、その出典番号(`source_idx`)がある。本文のターンには `[src=N]` が付くので、「新しい論点の出典番号が初めて出たターン」が話題の区切りの目安になる。ただし `[src=N]` が無い章もあり、確実ではない
  - ターン数・時間: 章は 14〜45 ターン、4〜5 分
- **区切り方の案**(勧める順):
  1. **時間で割る + ターンの境目に合わせる**: 章の長さ ÷ 約 90 秒で枚数を決め(1 章 1〜4 枚)、等分した位置に一番近いターンの頭で切る。意味は見ないが確実に動く。21 分の回で約 14 枚
  2. 1 に加えて、近く(±2 ターン)に `[src=N]` の変わり目があればそこに寄せる
  3. LLM に章全体を渡し、「2〜3 個の場面に分け、各場面の開始ターンと映すもの」を 1 回で返させる。区切りとプロンプトを同時に作れる。失敗したら 1 に戻す
- **時間の増分(6 → 12〜18 枚)**: 1 枚あたり「生成 4〜8 秒 + プロンプト用 LLM 数秒〜10 秒」で約 10〜15 秒。**6〜12 枚増えて +1〜3 分**(直列のまま)。エンコードは、映像トラックの入力が増えるだけでフレーム数は同じなので、ほぼ変わらない

### 3. 動き(パン・ズーム)
- **実装箇所**: `services/video_rendering/video_track_renderer.py` の `_build_concat_filter`。今は各画像に `scale,pad` をかけて `concat` でつないでいる。ここを画像ごとに「拡大 → ゆっくり動く切り抜き」に替える。章タイトル・字幕・日付は concat の後にかけているので影響しない
- **やり方は 2 通り**:
  - `zoompan`: 入力は今 `-loop 1 -t 秒` なので、`zoompan` を使うなら 1 枚の画像から `d = 秒 × 30` フレームを出す形に変える必要がある。整数に丸めるので画面が細かく揺れやすく、元画像を 4 倍ほどに拡大してからかけるのが定番。遅い
  - `scale`(少し大きめ、例 2112×1188) + `crop` の x / y を時刻 `t` の式で動かす: 今の `-loop 1` のまま使え、zoompan より軽い。ズームはできずパン(平行移動)だけ
  - 元画像が 768×432 なので、ズームは 1.0→1.1 倍程度までにする(それ以上はぼやけが目立つ)
- **エンコード時間とサイズへの影響**(見積もり。実測が要る):
  - 今は静止画なので、エンコード(libx264 ultrafast、映像トラックではコード内で固定。設定の use_gpu / NVENC は使っていない)はほとんど差分が無く速い
  - 動きを入れると、毎フレームの拡大・切り抜きと、全フレームが変わる分のエンコードが増える。21 分(約 37,800 フレーム)で、crop 方式は **+3〜8 分**、zoompan 方式は **+8〜20 分** と見ている
  - 最終の結合は映像をそのままコピーしている(`-c:v copy`)ので、**映像トラックのサイズがそのまま動画のサイズになる**。動きを入れると数倍になる可能性がある。CRF を上げるか、映像トラックを NVENC にする(`use_gpu` を映像トラックにも効かせる)と抑えられる
  - 決める前に、1 分ぶんだけ Windows で試しにエンコードして(fps・サイズ)を測るのが早い

### 4. 台本からの手がかり(verified_script.json に欄を足すなら)
- Windows 側のモデル(`core/models/verified_script.py`)は extra の指定が無い(Pydantic の既定で、**知らない欄は無視**)。radio_director が欄を足しても、今の Windows 側はそのまま動く。読む側の変更は、欄を足して loader(`build_script_segments`)で `ScriptSegment` まで運ぶだけ
- **最小の形の案**: 各セグメントに省略できる配列を 1 つ足す
  ```json
  "visuals": [
    {"turn_index": 0,  "scene": "小型の卓上 CO2 モニターが、ベッドから離れた棚の上にある寝室"},
    {"turn_index": 12, "scene": "換気のために少し開けた窓とカーテン"}
  ]
  ```
  - `turn_index` はそのセグメントの中で何ターン目から映すか(0 起点)。`scene` は日本語でよく、映すもの・置き場所・状態を書く
  - 無い・空のときは今までどおり(章 1 枚、プロンプトは本文の抜粋から作る)
  - 各ターンに `visual` 欄を足す形もあるが、台本本体(turns)をいじらずに済むので、セグメント側の配列を勧める
- **今のプロンプトとの関係**: `scene` は FLUX 用の英語プロンプトそのものにはせず、`ImagePromptGenerator` に「映すもの」として渡し、色・美学・前置き(人なし・文字なし)・長さの上限は今までどおり Windows 側で足す。radio_director は FLUX の都合を知らなくて済む。本文の抜粋はおまけ(雰囲気用)に下げる
- 仕様書(interface_spec.md)と radio_director 側のモデルの両方の変更が要る(Windows だけでは閉じない)

### 5. 絵の内容の精度
- **ずれの原因は指示文にある**(画像モデルの限界より先に):
  - **例が寝室**: 指示文の例 1(医療の話題)が「**枕元のテーブル**にセンサーとインスリンペン、奥に乱れたベッド」。健康・医療寄りの話題では、LLM がこの例に引っ張られやすい。「イントロでモニターが枕元」はこれで説明がつく
  - **画面の禁止**: 「画面・モニター・表示の無いこと。機器は電源が切れているか、背面・側面だけ」という決まりがある。CO2 モニターは表示部が特徴の機器なので、表示部を消すと**正体の分からない箱**になる
  - **医療寄りの構図の指示**: deep_dive の構図の指示が「医療の話題なら器具・試料・小瓶・装置を細部まで」。健康の話題が医療機器の見た目に寄る
  - **章の頭しか見ていない**: 1 のとおり先頭 800 字だけ。「ベッドから離れた棚」が章の後半で出てきても、LLM には届いていない
- **具体物の指定で直るか**: かなり直る見込み。FLUX は T5 でプロンプトを読むので、「手のひら大の白い卓上空気質モニター、小さな暗い表示窓」「部屋の反対側の棚の上、ベッドはぼかして奥」のような、物・大きさ・材質・置き場所の指定はおおむね効く。ただし 4 ステップ・768×432 なので、小さな物の細部や「離れている」のような位置関係は外れることがある。物を画面の主役(画面の 4〜6 割)にする指定と合わせるのがよい
- **表示部を許すか**: 表示を許すと、FLUX は数字らしき崩れた文字を描きやすい。「表示窓は暗い / 色の付いた光だけ」と書けば多くは防げるが、ゼロにはならない
- **ネガティブプロンプトの現状**: ワークフローのノード 7 に `text, watermark` があるが、**cfg 1.0 では使われていない**(ComfyUI は cfg 1.0 のときネガティブ側を計算しない。schnell は cfg 無しで学習したモデルで、ネガティブプロンプトは元々効かない)。「人なし・文字なし」は全部、正のプロンプトの先頭の前置き("no people, no hands, ... no screen interfaces")に頼っている。否定の語を並べると、かえってその物を呼び込むことがある(「screen」「faces」と書いている)
